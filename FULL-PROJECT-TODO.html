B · Orders you can't fulfil correctly

These are live now. Each one loses you information you need before you can ship.

  • The option the customer picks never reaches the order

    Loses data

    A customer choosing a ring size sees "Size 7" in their bag — the cart really does display it. But checkout rebuilds each line as id, name, price, qty, image and throws variant away. The order arrives with no size on it, and the customer has no idea. You cannot ship the ring.

    FixAdd variant: i.variant to the mapped item in Checkout.jsx, then show it in the order rows in OrderManager.jsx so you actually read it while packing.

    src/Pages/Checkout.jsxsrc/Component/OrderManager.jsx

  • The watch finish selector is a lie

    Wrong data

    On a watch page the colour swatches are genuinely clickable and change the selection — but the code that adds to the bag hardcodes variant: "Finish: Rose Gold". Pick a black watch, and your order says Rose Gold. You ship the wrong finish and it looks like your mistake.

    FixDerive the label from the chosen swatch instead of the hardcoded string — and read the real colour list from the database (see C2) rather than the invented defaults.

    src/Pages/ProductDetails.jsx

  • Sold-out products can still be ordered

    Loses money

    Stock is managed in the admin and nowhere else. No storefront page reads it: no "sold out" badge, no disabled Add to Bag, nothing at checkout. A customer can buy the last item twice and you only find out when stock goes negative.

    FixShow stock on the product page, block Add to Bag at zero, and re-check quantities at checkout.

    src/Pages/ProductDetails.jsxsrc/Pages/Checkout.jsx

  • Stock can oversell and ignores quantity

    Loses money

    After an order the stock is read, then written, and only when it is above zero. Order 5 when you have 3 and it clamps to 0 — the other 2 sales are silently unfilled, and two simultaneous orders can overwrite each other.

    FixCheck the requested quantity against stock before it can be added to the bag. The robust version is a database function that decrements atomically — worth doing before you run ads.

    DoneBoth halves are in: the basket refuses to add more than the shop has, and the order now takes stock off through decrement_product_stock() — one atomic statement in Postgres, so two orders landing in the same second can no longer both read the old number. Until A2 is run the app quietly falls back to the old read-then-write.

    src/stores/productStore.jssrc/stores/cartStore.jsSUPABASE_MIGRATION.sql

  • Orders placed during an outage vanish

    Loses orders

    If the database is unreachable, the order is kept in the customer's own browser instead and they still get a confirmation screen and an order number. You never see it. Neither of you knows anything went wrong — which is exactly what would be happening right now if customers were ordering today.

    FixDetect the failure and tell the customer the order did not reach you, with your phone number. Never show a confirmation for an order that was not saved.

    src/stores/productStore.jssrc/Pages/Checkout.jsx

  • Customer passwords are stored in plain text

    Done

    Accounts were kept in the browser's localStorage with the password readable as typed. Anyone using that device could read every password.

    DonePasswords are now stored as SHA-256 hashes, never as typed, and an account created before this change is upgraded to a hash the next time that customer signs in.
